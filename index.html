How this measurement works

Every engine draws the same gear, inlined into its JavaScript bundle as a data URL. Each engine passes that data URL to its own image loader, so every page decodes and uploads the identical image, and the only requests are the HTML and the bundle.

The clock starts at navigation and stops once the first frame showing the gear has finished on the GPU. Each engine reports from its normal render loop after drawing that frame; a shared hook waits for the render stack to return, then calls WebGL finish(). The time therefore covers HTML and script download and parse, engine boot, image decode and texture upload, shader compilation, drawing, and GPU completion.

Each sample runs in a fresh browser with an empty HTTP cache and service workers blocked, so code and shaders load cold every time. A blank WebGL page runs first so GPU process start-up is excluded, as in an already-open browser. Engine order rotates each round. OS, DNS and GPU driver caches are not reset.

Network profiles apply bandwidth and latency limits through Chromium DevTools; CPU is not throttled. Responses are gzipped. Because the image travels inside the bundle, throttled profiles mostly reflect bundle size.

How this measurement works

Every engine runs the same simulation: sprites with random velocity and spin, bouncing off the edges of a 640 × 360 WebGL canvas. The simulation lives in shared typed arrays; each engine only creates its ordinary sprite objects and copies x, y and rotation into them once per frame, so the scene graph, batching and draw path of the engine are what differ. Special-purpose batching objects such as PixiJS ParticleContainer or Phaser SpriteGPULayer are not used.

Headless Chromium caps requestAnimationFrame at the display rate, so frame time cannot fall below one vsync. The page first measures the empty-scene frame rate, then holds 1,000 sprites, 2,000, 4,000 … each for a 0.5 s warm-up and a 1 s sample, until the frame rate falls under 90 % of the empty-scene rate, and bisects three times between the last passing and first failing count. The reported value is the largest passing count; hover a row for the frame rates. Network profiles only affect page load here, not the measurement.
